OKF Fact-Checking Bundle Specification

Version: observer-disagreement-framework OKF-FC profile 0.1.1.

Upstream target: Open Knowledge Format (OKF) Version 0.1 - Draft, checked against GoogleCloudPlatform/knowledge-catalog/okf/SPEC.md at upstream commit d44368c15e38e7c92481c5992e4f9b5b421a801d on 2026-07-21. Version 0.1.1 adds the mandatory Wolfram observer-theory foundation disclosure for all future bundles. This profile is a stricter, project-specific OKF v0.1 profile. OKF permits producer-defined frontmatter keys and requires consumers to tolerate unknown keys and broken cross-links; every project-specific key defined here is namespaced with fc- to avoid future upstream-key collisions.

This document is normative for fact-checking and statement-evolution bundles in this repository. It is implementable without reading the design discussion in docs/framework_v3.md, though that document remains the theoretical rationale.

1. Normative Language

The words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL are normative and have their ordinary specification meanings:

Term Meaning
MUST / REQUIRED / SHALL A conforming full-profile or lightweight-profile bundle is invalid if it violates the rule.
MUST NOT / SHALL NOT A conforming bundle is invalid if it performs the forbidden action.
SHOULD / RECOMMENDED A conforming bundle may violate the rule only with an explicit reason recorded in the relevant concept or round. Validators report violations as warnings.
SHOULD NOT / NOT RECOMMENDED A bundle may do this only with recorded rationale. Validators report occurrences as warnings.
MAY / OPTIONAL The behavior is permitted and may be absent without validation impact unless another rule makes it applicable.

2. Bundle Identity and Profiles

An OKF-FC bundle is a directory describing one fact-checking, reproduction, or statement-evolution problem. Its concept identity is the path of each Markdown file relative to the bundle root, without the .md suffix, following OKF v0.1.

Two profiles are defined.

2.1 Full Profile

The full profile is REQUIRED for contested, high-stakes, long-running, or research-relevant trajectories. It MUST include:

  • the PF, S, R, REPRO, and INQUIRY axes;
  • log.md;
  • inquiry/index.md;
  • one inquiry/round-NNNN.md file for every bundle round;
  • append-only supersession metadata on every revised current concept;
  • enough pinned reproduction metadata to re-derive or explicitly mark the result as unreproducible.

2.2 Lightweight Ledger-Only Profile

The lightweight profile MAY be used for low-stakes trajectories where per-round files would add cost disproportionate to risk. It MUST include:

  • index.md, answer.md, log.md, and at least one PF, S, R, or REPRO concept file needed to understand the current state;
  • a log.md ledger row for every bundle round;
  • all concept frontmatter fields required by this specification;
  • fc-stage in each ledger row or ledger row prose for every v3-or-later round;
  • fc-type-at-round only for ledger rows whose stage is contestation.

The lightweight profile MUST NOT use fc-type-at-round for non-contestation rounds. It MAY omit inquiry/round-NNNN.md files and inquiry/index.md.

2.3 Upgrade Path

A lightweight bundle may be upgraded to the full profile by a new recorded bundle round. The upgrading round MUST:

  1. create inquiry/index.md;
  2. create one inquiry/round-NNNN.md file for the upgrading round;
  3. either backfill earlier per-round files from the ledger or explicitly mark earlier files NOT AVAILABLE;
  4. preserve all original ledger rows and round numbers;
  5. mark any inferred backfilled field UNVERIFIED;
  6. update current concepts with fc-round equal to the upgrade round only when their content or metadata materially changes.

Backfilling MUST NOT invent evidence, checksums, parties, classifications, or commit pins. A validator treats missing historical full-profile round files as warnings after an upgrade if the upgrading round documents why they are not available.

The full-profile layout is:

<bundle-id>/
|-- index.md
|-- answer.md
|-- agent-contract.md
|-- log.md
|-- pf/
|   |-- index.md
|   |-- overview.md
|   |-- formal.md
|   `-- full-context.md
|-- s/
|   |-- index.md
|   |-- overview.md
|   |-- method.md
|   `-- specification.md
|-- r/
|   |-- index.md
|   |-- overview.md
|   |-- results.md
|   `-- full-results.md
|-- reproduction/
|   |-- index.md
|   |-- code.md
|   |-- data.md
|   `-- environment.md
`-- inquiry/
    |-- index.md
    |-- round-0001.md
    |-- round-0002.md
    `-- ...

Required files for the full profile: index.md, answer.md, agent-contract.md, log.md, every axis index.md, at least one non-index concept in each PF/S/R/REPRO axis, inquiry/index.md, and all contiguous round files from round-0001.md through the current bundle round.

Optional files: additional concept files under any axis, deeper subdirectories, r/full-results.md and reproduction/environment.md when there are no full results or runnable environment facts yet, and derived artifact directories such as _site/. Optional omissions MUST be visible in the relevant axis index or current status when they affect interpretation.

Reserved OKF filenames: index.md and log.md have no frontmatter. All other .md files are concept documents and MUST have parseable YAML frontmatter with a non-empty type.

4. Axes and Disclosure Levels

4.1 Axes

Axis Path Purpose Required in full profile
PF pf/ Problem formulation: claim, scope, definitions, and question boundaries. Yes
S s/ Solution/method: algorithm, frame, assumptions, specification, and conventions. Yes
R r/ and answer.md Results: current answer, verdict, uncertainty, and status. Yes
REPRO reproduction/ Reproduction: code, data, environment, commands, provenance, source commits, checksums. Yes
INQUIRY inquiry/, log.md, agent-contract.md Statement trajectory: rounds, moves, stages, parties, supersession, ledger. Yes

4.2 Levels L0-L3

fc-level uses integers, not strings:

Level Meaning Typical location Validation
0 L0: complete compressed answer for a lay reader. answer.md Required for root answer.
1 L1: plain overview. */overview.md Recommended for PF/S/R.
2 L2: method, formal, result, or reproduction detail. pf/formal.md, s/method.md, r/results.md, reproduction/*.md Recommended.
3 L3: full context, exact specification, per-item detail, edge cases. */full-*.md, s/specification.md Optional unless required by the bundle problem.

Each current deeper level MUST refine rather than contradict the current shallower level. If deeper work finds a contradiction, the fix is a new round and supersession, never a silent edit.

5. Required Frontmatter Fields

All non-reserved .md files MUST contain parseable YAML frontmatter. Unknown frontmatter keys are allowed by OKF, but project keys MUST use the fc- namespace unless they are upstream OKF keys (type, title, description, resource, tags, timestamp).

5.1 Shared Fields

Field Type Allowed values Applicability Validation behavior
type non-empty string Descriptive OKF type, e.g. Finding, Runbook, Event, Policy, Specification Required on every concept file Fatal if absent, empty, or frontmatter malformed
title string Any concise display title Recommended on every concept Warning if absent
description string One-sentence summary Recommended on every concept Warning if absent
timestamp ISO 8601 date or datetime string e.g. 2026-07-21 Recommended on current concepts and required on round files Warning on concepts if absent; fatal on v3-or-later round files
resource URI or path string Pinned URI, bundle-relative path, or repository-relative path Optional; required when the concept describes an external asset Warning if unpinned when external evidence is cited
tags YAML list of strings Producer-defined Optional Advisory if malformed but parseable YAML may already fail earlier
fc-axis string PF, S, R, REPRO, INQUIRY Required on every concept except reserved index.md and log.md Fatal if absent or not one of the allowed values
fc-level integer 0, 1, 2, 3 Required on PF/S/R/REPRO concepts and answer.md; forbidden on round files unless a bundle documents a special view Fatal if absent where required or outside range; warning if present on a round file
fc-status string open, resolved, underdetermined, superseded Required on current concepts and round files Fatal if absent or outside set; advisory if a current index says a different status
fc-round integer positive bundle-local integer Required on all current concepts and round files Fatal if absent, non-integer, less than 1, or confused with a repository round
fc-irreducibility string none, computational, factual, mixed, unknown Required when a concept asserts a reproduction obstacle, underdetermined closure, or irreducibility classification; recommended on REPRO concepts; optional elsewhere Fatal if malformed or absent where an irreducibility claim is made; warning if a REPRO concept omits it; warning if unknown lacks rationale
fc-supersedes string or YAML list of strings <concept-path>.md@r<bundle_round> Required when a concept materially revises a prior current version; absent otherwise Fatal if malformed; fatal for duplicate supersession of the same prior concept in current state; warning if referenced prior version cannot be found in git history
fc-touches YAML list of paths Bundle-relative concept paths Required on round files; optional elsewhere Fatal if absent on v3-or-later round files; warning for unresolved paths

fc-status: superseded MAY be used in archived explicit files if a bundle keeps old versions in the tree. The normal repository practice is to preserve old versions in Git history and keep only the current concept file at the path.

5.2 Round Fields

Round files are inquiry/round-NNNN.md in the full profile. Lightweight profile ledger rows MUST carry equivalent data in table columns or prose.

Field Type Allowed values Applicability Validation behavior
fc-move string question, objection, evidence, frame-change, convention, verdict-revision Required on every v3-or-later round Fatal if absent or malformed
fc-stage string formation, enrichment, critique, contestation, consolidation Required on every round opened under v3 or later; optional-tolerated on pre-v3 round files Fatal if absent on v3-or-later round; warning if absent on pre-v3 round
fc-party string Stable party id; see party identity Required on every round Fatal if absent or empty
fc-type-at-round string I, II, III, resolved Required only when fc-stage: contestation; forbidden otherwise Fatal if absent on contestation; fatal if present on non-contestation
fc-touches YAML list of paths Paths touched by the round, or [] Required on every round Fatal if absent; warning for unresolved paths

fc-type-at-round is forbidden when fc-stage is formation, enrichment, critique, or consolidation because there is no live counter-position to classify. This is a fatal validation error, not a style warning.

6. Stages, Moves, and Types

fc-stage classifies the lifecycle role of the round. fc-move records the operational action. The same move can realize different stages.

fc-move Permitted fc-stage values Rule
evidence formation, enrichment, contestation Formation only for first emission; enrichment when adding support/context without rival position; contestation when evidence is offered against a standing rival position.
question enrichment, critique Enrichment when filling missing context; critique when probing the frame or assumptions without maintaining a rival claim.
objection critique, contestation Critique when no rival position remains standing; contestation when a counter-position is maintained.
frame-change contestation, consolidation Contestation when a divergent frame is asserted; consolidation when a frame is adopted as settlement.
convention consolidation Convention adoption is consolidation.
verdict-revision consolidation Verdict revision is consolidation.

Validators MUST reject unlisted move/stage pairs as fatal errors unless the round explicitly marks the pairing UNVERIFIED and predates this specification; that grandfathering is a warning, not a license for new rounds.

Contestation types:

Type Meaning Closure behavior
I Context-window divergence over accessible records. Data sharing may resolve it.
II Frame or compression-function divergence over shared records. Translation or adopted convention may resolve it.
III Needed content is absent from the surviving record. Must be marked underdetermined or convention-resolved; more data or frames cannot restore absent facts.
resolved A formerly live contestation has been resolved in this contestation round. The round must state what resolved and what, if anything, remains open.

7. Party Identity

A party is the observer or agent responsible for a round. fc-party MUST be a stable, lower-case identifier such as codex, claude, human, reviewer-a, or an organization id. It MUST NOT encode transient branch names, chat ids, or private memory. If a human acts through an agent, the recorded party SHOULD distinguish the actor when material, for example human for explicit human content and codex for agent-authored implementation or classification.

Proxy observers that only consume the bundle do not become parties. A participating observer becomes a party when it adds evidence, asks an inquiry extending question, raises an objection, changes a frame, adopts a convention, revises a verdict, or edits concepts as part of a recorded move.

8. Repository Rounds and Bundle Rounds

Repository rounds and bundle rounds are separate counters.

Counter Location Meaning
repo_round root log.md Every merged repository change.
bundle_round bundles/<id>/log.md and bundles/<id>/inquiry/round-NNNN.md Moves in one bundle's statement trajectory.

fc-round in a bundle concept or round file is always the bundle round, never the repository round. Root log.md rows use the repository round in their round column. Snapshot names use the bundle round. Snapshot manifests and catalog rows MUST record the source repository round separately when available.

The next round number MUST be computed from HEAD of main at the time the work starts. Agents MUST NOT hard-code numbers from prompts, digests, exported HTML, or prior conversations.

9. Current-Version Resolution

The current version of a concept is the file at its path in the committed HEAD of main, interpreted with its frontmatter and any fc-supersedes pointer. Git history preserves prior text unless a bundle explicitly stores old versions as separate archived concepts.

If multiple files claim to be the current version of the same concept, a validator MUST report a fatal inconsistent-current-concepts error unless one is clearly marked fc-status: superseded and excluded from the current index.

Current bundle status is resolved from:

  1. answer.md for the compressed current answer;
  2. axis concepts for current PF/S/R/REPRO state;
  3. inquiry/index.md and bundle log.md for trajectory history;
  4. Git history only for recovering superseded prior versions.

10. Append-Only Round Rules

Full-profile round files MUST be contiguous: round-0001.md, round-0002.md, and so on, with no gaps through the current bundle round. They MUST NOT be renumbered, deleted, or rewritten after merge except by an explicit later repository change that records the repair as a new round and explains the reason.

Every material change to a bundle's self-description or claim state MUST append the next bundle round, update bundle log.md, and update inquiry/index.md. Infrastructure-only changes that do not materially change a bundle MAY skip a bundle round, but they still receive a repository round when merged.

Lightweight-profile ledgers MUST preserve the same append-only numbering even without per-round files.

11. Supersession Rules

Supersession is append-only revision of current concepts.

  • A concept that materially revises an earlier current concept MUST set fc-round to the current bundle round and fc-supersedes to the replaced concept and round, e.g. s/specification.md@r8.
  • A round that causes supersession MUST list the touched concepts in fc-touches and describe the revision under # Resulting revisions.
  • A prior concept SHOULD be superseded by exactly one successor in the current line of descent. Duplicate supersession of the same prior version is fatal unless the round states that one successor was itself superseded and no longer current.
  • Consolidation is not terminal. A consolidated concept MAY be superseded by a later critique, contestation, enrichment, or consolidation round.
  • Silent edits to current concepts are forbidden when the edit changes meaning, status, evidence, method, verdict, or classification.

12. Underdetermined Closure and Evidence Notation

A contestation bottoms out when the residual disagreement is invariant under available evidence moves and frame moves because the needed content is absent from the surviving record. A bundle MUST mark this state explicitly:

  • use fc-status: underdetermined on the relevant current concept or round;
  • use fc-irreducibility: factual or mixed;
  • state what is absent from the surviving record;
  • avoid language implying empirical proof beyond the surviving record.

Notation requirements:

Label Meaning Validation
PROVISIONAL A claim is proposed but may be sharpened by later rounds. Advisory if overused on current verdicts.
UNVERIFIED The bundle has not checked the claim or source. Warning when used for required reproduction pins.
NOT MEASURABLE The desired measurement cannot be computed from available data or method. Must include reason.
NOT AVAILABLE The information, artifact, checksum, or commit is unavailable to the bundle. Must include reason and irreducibility classification.

Bundles MUST NOT invent references, empirical results, checksums, classifications, measurements, or source commits. Missing evidence is recorded as missing evidence, not filled by plausible prose.

13. Canonical State and Derived Artifacts

The committed HEAD of main is the canonical current state. A branch, working tree, rendered _site/, exported zip, catalog, visualization, or published snapshot is not canonical unless it records the exact source commit and that commit is the relevant HEAD under inspection.

Derived artifacts MUST:

  • record source_commit as a full Git commit hash;
  • record source_repo_round when published or cataloged after merge;
  • record bundle_round from the bundle ledger;
  • record checksums for packaged files or provide a manifest whose own checksum is recorded by the publishing process;
  • be considered stale when source HEAD changes past source_commit;
  • be regenerated by documented commands rather than manually edited.

During an unmerged PR, a new source-commit pin for artifacts generated from the future merge commit is NOT AVAILABLE. Do not fabricate it. A renderer may still update local inspection HTML from the working tree, but that HTML is working-tree derived until a committed/published artifact pins a source commit.

14. Source Commits, Checksums, and External Evidence

REPRO concepts MUST pin:

  • repository URLs and exact commits for code;
  • dataset versions, access dates, and checksums for data when checksums are available;
  • commands, environments, lockfiles, or explicit NOT AVAILABLE labels for reproduction conditions;
  • source document checksums when source documents are treated as inputs.

An external citation that supports a material result SHOULD be a stable primary source or original scholarly work. If an external source is unpinned, the bundle MUST mark the evidence UNVERIFIED or explain why pinning is not available. Unpinned external evidence is a validation warning; unpinned REPRO evidence for a current result is fatal unless explicitly marked NOT AVAILABLE with factual or computational irreducibility rationale.

15. Wolfram Observer-Theory Foundation

Every bundle generated under the full observer-disagreement and statement-evolution framework MUST contain a Wolfram observer-theory foundation concept at exactly:

s/foundations/wolfram-observer-theory.md

This page is mandatory for both full-profile and lightweight-profile bundles. No bundle may omit it by pointing only to an external Wolfram source, to a repository-level document, or to another foundation page. In particular, s/foundations/ait-compression.md, s/foundations/coarse-graining-statmech.md, and s/foundations/second-order-cybernetics.md MUST NOT be treated as substitutes for s/foundations/wolfram-observer-theory.md.

The required claim is narrow: the framework uses identified Wolfram computational concepts as a formal analogy for bounded observers, coarse-graining, irreducibility, and computational possibility. A conforming bundle MUST NOT imply that Wolfram's fundamental-physics program is empirically established, or that the social, institutional, scientific, or historical subject matter of the bundle literally instantiates Wolfram-model physics.

15.1 Required Foundation Frontmatter

The Wolfram foundation page MUST include at least this frontmatter:

---
type: Concept
title: Wolfram observer theory
description: Cross-cutting observer-theory foundation used as a formal analogy.
fc-level: 2
fc-axis: S
fc-foundation: wolfram-observer-theory
fc-foundation-role: formal-analogy
fc-foundation-template-version: "1.0.0"
fc-foundation-template-modified: false
fc-foundation-bundle-additions: []
fc-foundation-source-registry-version: none
fc-status: open
fc-round: 1
timestamp: 2026-07-23
---

All project-specific metadata on this page MUST use the fc- namespace. fc-foundation-template-version records the canonical template version used by generator tooling. fc-foundation-template-modified records whether the generic foundation text was changed. fc-foundation-bundle-additions records bundle-specific additions, either as a YAML list or a concise scalar summary. fc-foundation-source-registry-version records the source-registry version when a registry exists; otherwise it MUST be none or NOT ADOPTED.

15.2 Required Sections

The page MUST contain these top-level sections in this order:

## Role in this framework
## Directly sourced Wolfram concepts
## Formal translations made by this project
## Project extensions not derived from Wolfram
## Non-claims and limitations
## Source map
## Relevance to this bundle

Relevance to this bundle MUST be bundle-specific. It MUST identify which observer concepts the bundle actually uses: for example context windows, compression/framing functions, observer trajectories, ruliad/rulial-space analogy, computational irreducibility, or provenance/recording-function extensions. Generic boilerplate alone is non-conformant.

15.3 Attribution Classes

Every row in the Source map table MUST use exactly one of these attribution classes:

Class Meaning
direct Wolfram concept The source claim is made in an identified Wolfram primary source.
project translation The project maps a direct or adjacent source concept into its own formal notation or bundle discipline.
project extension The project introduces a claim, taxonomy, notation, or practice that is not derived from Wolfram.
independent comparison A non-Wolfram source is used to compare, contextualize, criticize, or formalize related ideas.
provisional inference The bundle makes a tentative inference from sources and marks the uncertainty explicitly.

15.4 Minimum Source Policy

The foundation page MUST follow this source policy:

  • A YouTube transcript MAY be supplementary but MUST NOT be the sole source.
  • Source attribution MUST include stable bibliographic identity: DOI, arXiv identifier, ISBN plus chapter/section, or a dated canonical publication page.
  • At least one source MUST support computational irreducibility.
  • At least one source MUST support computational boundedness and observer coarse-graining/equivalencing.
  • At least one source MUST support ruliad or rulial-space terminology whenever that terminology appears.
  • Independent commentary MUST be distinguished from Wolfram primary sources.
  • Direct quotation is OPTIONAL and SHOULD be avoided unless exact wording is needed.
  • Inaccessible or uncertain attribution MUST be marked UNVERIFIED, not silently inferred.

15.5 Analogy Guardrails

A conforming page MUST explicitly state all of the following:

  • The framework does not identify human disagreement or statement evolution literally with Wolfram-model physics.
  • No measured rulial metric between human observers is asserted.
  • The validity of the bundle does not depend on acceptance of Wolfram's fundamental-physics program.
  • Factual irreducibility, the recording function r, the surviving-record model R = r(E), the disagreement taxonomy, the stage taxonomy, and the OKF round/supersession/provenance discipline are project extensions.

15.6 Full and Lightweight Profiles

A full-profile bundle MUST use the complete canonical foundation template and then add bundle-specific relevance. A lightweight or ledger-only bundle MAY use shorter prose, but it MUST still include:

  • the required frontmatter;
  • the formal-analogy disclaimer and all analogy guardrails;
  • the required attribution-class separation;
  • a minimum source map satisfying section 15.4;
  • a bundle-specific Relevance to this bundle section.

There is no lightweight-profile exemption allowing omission of the foundation page.

15.7 Canonical Template and Drift Control

Generator tooling MUST emit s/foundations/wolfram-observer-theory.md from a versioned canonical template. A generated or migrated page MUST record:

  • fc-foundation-template-version;
  • whether generic foundation text was modified via fc-foundation-template-modified;
  • bundle-specific additions via fc-foundation-bundle-additions;
  • source registry version via fc-foundation-source-registry-version, if a source registry is adopted.

Validators SHOULD warn when a page records fc-foundation-template-modified: true without explaining the modification in frontmatter or prose. Validators MUST reject missing required foundation frontmatter, missing required sections, invalid attribution classes, absence of the mandatory source-map support, a YouTube transcript as the sole citation, attempts to substitute AIT/coarse graining/second-order cybernetics for the Wolfram page, and generic relevance text with no bundle-specific observer concepts.

Historical bundles are not silently rewritten. Existing bundles migrate by a recorded bundle round that adds or supersedes the foundation page, updates the bundle ledger, and states what historical material is superseded. Validators MAY warn on pre-0.1.1 bundles that lack the page, but future generated bundles and post-migration current bundles MUST satisfy this section.

16. Internal Links

OKF v0.1 requires consumers to tolerate broken links. Therefore unresolved internal links are warnings, not fatal errors, when the link is otherwise well-formed Markdown and the target may be not-yet-written knowledge.

Broken links become fatal only when:

  • the link target is required by a current fc-supersedes pointer;
  • the link target is required by fc-touches for a v3-or-later round;
  • the link claims to pin required reproduction evidence and no fallback label is present.

17. Agent Behavior

17.1 Proxy Observer

A proxy observer consumes a bundle without extending its trajectory. It MUST:

  1. start from index.md or answer.md;
  2. classify the user question by level and axis;
  3. descend only as deep as the question requires;
  4. answer from the concept file used and cite the path;
  5. offer deeper inspection only when useful.

It MUST NOT answer deeper than asked, because that imposes its own coarse-graining, and MUST NOT answer shallower than required, because that loses information the user requested.

17.2 Participating Observer

A participating observer extends the bundle. It MUST:

  1. compute the next bundle round from HEAD;
  2. record the move in the next round file or lightweight ledger row;
  3. classify fc-move and fc-stage;
  4. include fc-type-at-round only if fc-stage: contestation;
  5. record fc-party;
  6. apply concept revisions through supersession;
  7. update bundle log.md and inquiry/index.md;
  8. update root log.md using the next repository round when the PR merges;
  9. preserve missing or uncertain evidence with explicit labels rather than invention.

18. Round Record Body Schema

Full-profile round files MUST contain these top-level sections in this order:

# Move
# Evidence added
# Effect on state
# Resulting revisions
# Classification rationale

# Move records the question, objection, evidence, frame-change, convention, or verdict revision, either verbatim or by pinned link. # Evidence added lists links, checksums, source commits, and missing-evidence labels. # Effect on state states changes to the context window C(t) and frame f(t). # Resulting revisions lists superseded concepts or says no concept content changed. # Classification rationale explains the stage and, for contestation only, the type.

19. Validation Contract

Validators MUST separate fatal errors, warnings, and advisory quality checks.

19.1 Fatal Validation Errors

  • malformed YAML frontmatter on a concept file;
  • missing or empty type;
  • missing required fc-axis, fc-level, fc-status, fc-round, or applicable fc-irreducibility;
  • fc-stage absent on v3-or-later rounds;
  • malformed fc-stage or fc-move;
  • unlisted fc-move/fc-stage pair on a new round;
  • fc-type-at-round present when stage is not contestation;
  • fc-type-at-round absent when stage is contestation;
  • round numbering gaps or duplicate round numbers;
  • duplicate current concepts for the same concept identity;
  • malformed fc-supersedes;
  • duplicate supersession of the same prior concept in the current line;
  • inconsistent current concepts where no file is clearly superseded;
  • required reproduction code/data lacks a commit, checksum, or explicit NOT AVAILABLE rationale;
  • a derived artifact claims to be pinned but lacks source_commit;
  • required fc-touches or fc-supersedes target is unresolved;
  • s/foundations/wolfram-observer-theory.md is missing from a future generated or post-migration bundle;
  • another foundation page or an external link is used as a substitute for the mandatory Wolfram foundation page;
  • required Wolfram foundation frontmatter, sections, attribution classes, or source-map support are missing;
  • a YouTube transcript is the sole source for the Wolfram foundation page;
  • the Wolfram foundation page omits the formal-analogy guardrails or lacks bundle-specific relevance.

19.2 Warnings

  • unresolved ordinary internal links;
  • stale generated artifacts whose source_commit differs from current HEAD;
  • unpinned external evidence not required for a current result;
  • UNVERIFIED, NOT MEASURABLE, or NOT AVAILABLE without adequate prose rationale;
  • absent title or description;
  • absent fc-stage on pre-v3 historical round files;
  • optional full-profile files omitted without an axis-index note;
  • lightweight profile used for a high-stakes or contested trajectory without rationale.

19.3 Advisory Quality Checks

  • shallow levels are too terse to answer their intended reader;
  • deeper levels repeat rather than refine;
  • stage rationale is conclusory;
  • contestation type rationale does not identify context, frame, or missing record;
  • party identity is too vague for later attribution;
  • source citations prefer secondary summaries where primary sources are available;
  • provisional labels remain on old current concepts without follow-up.
