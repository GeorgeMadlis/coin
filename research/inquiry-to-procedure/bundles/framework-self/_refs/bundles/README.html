Portable snapshots

okf-fc snapshot <bundle_dir> -o <out_dir> [--zip <zipfile>] produces a self-contained, zip-portable inspection artifact: every out-of-bundle link target that the plain renderer would otherwise leave pointing at the local filesystem (e.g. reproduction/data.md's pinned link into docs/framework_v2.md) is instead vendored into <out_dir>/_refs/<repo-relative-path> and the link rewritten to the vendored copy, one level deep (links inside a vendored page that would require vendoring a second time are left as visibly-unresolved spans instead, so a snapshot cannot grow without bound). The result — unzipped anywhere and opened via file:// with no server — lets a reader reach every textual file of the bundle by clicking through, with fixed archive timestamps so identical inputs produce byte-identical zips. Alongside the HTML, okf-fc snapshot writes manifest.json (every source file's SHA256, the source repo commit, and the bundle's current highest round and status) and structure.svg/structure.html — a deterministic columnar diagram of the bundle's concept files grouped by axis (PF/S/R/REPRO/ INQUIRY) and disclosure level, with edges for markdown links, fc-supersedes, and fc-touches. okf-fc render --self-contained performs just the link-vendoring step without the manifest or visualization, for a lighter-weight portable render.

Publishing to the viewer repository

okf-fc publish <bundle_dir> --dest <snapshots_repo> publishes a bundle's committed HEAD as a pinned snapshot into the sibling ../okf-bundle-snapshots repository: a self-contained snapshot (as above) plus its deterministic zip under <dest>/<bundle-id>/<YYYY-MM-DD>-r<NNNN>-<shorthash>/, where <NNNN> is the bundle's highest bundle-local inquiry round and <shorthash> is the source repo's HEAD commit at publish time. The manifest/catalog also record source_repo_round, the latest root log.md round at that commit; see docs/round-ledgers.md for why repository rounds and bundle rounds intentionally diverge. It refuses to run against a dirty git worktree — pass --allow-dirty to override — because only committed HEAD is publishable (docs/agent-guide.md's Canonical-State Rule); an unpinned snapshot would itself become a future Type III dispute about its own provenance. Publishing never rewrites an existing snapshot directory or zip.

Every publish also rebuilds that repo's metadata catalog (okf-fc catalog rebuild --dest <repo> runs the identical code path): catalog.db (SQLite; query with okf-fc catalog query --dest <repo> "<SELECT ...>", read-only) and catalog.json (the same content, flat and diff-friendly). The snapshots table stores both round (bundle round, also used in the snapshot filename) and source_repo_round (root log.md round at the pinned commit). Publishing also rebuilds each bundle's evolution.svg — a per-party swimlane diagram of its bundle-round sequence, colored by fc-stage and annotated with fc-move, fc-type-at-round (contestation rounds only), and supersession events — and the top-level and per-bundle index.html pages. Publishing does not commit in the destination repo; it prints the git add/git commit commands to run there. See ../okf-bundle-snapshots/README.md for the catalog schema and example queries.
